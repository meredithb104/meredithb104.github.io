Accessibility statement

This site is built to WCAG 2.2 Level AA

I'm a blind accessibility engineer, so this page is the one I care most about getting right. This statement names the standard to which the site conforms, explains how I checked, lists what I know is imperfect, and tells you how to reach me when something is wrong. Last reviewed: 17 September 2026.

Conformance

meredithb104.github.io is intended to conform to the Web Content Accessibility Guidelines (WCAG) 2.2 at Level AA, and meets several AAA criteria where they were cheap to meet: body text contrast of 7:1 or better in every theme (1.4.6), 44-pixel targets (2.5.5), and no time limits or motion beyond short transitions that stop entirely under prefers-reduced-motion (2.3.3).

What the site does

  • Semantic HTML with one h1 per page, landmarks for header, navigation, main, and footer, and a skip link that lands on a focusable main.
  • A single visible focus indicator on every interactive element, 3 pixels wide with a 2-pixel offset, contrast-checked against every background it can appear on (2.4.7, 2.4.11, 2.4.13).
  • In-page navigation moves keyboard focus to the target section. Below 72em the navigation collapses behind a "Menu" button (a disclosure with aria-expanded; Escape closes it and returns focus), the header is not sticky, and without JavaScript the full list simply shows. At 72em and above the header is sticky only because the full navigation fits on one row, so it cannot obscure a focused element (2.4.11).
  • Three themes (light, dark, high contrast) compiled from one token file; the build fails if any text/background pair drops below its required ratio. Windows forced-colors mode is styled with system colors rather than overridden.
  • Every state is expressed in text as well as color: Pass and Fail in the contrast checker, a check mark and bold weight on the active filter, an underline on the current section (1.4.1).
  • Nothing here is disabled while it works, and no control requires dragging, a specific pointer, or a path-based gesture (2.5.1, 2.5.7).
  • Content reflows to a 320-pixel-wide viewport with no horizontal scrolling, survives 200% zoom and user text-spacing overrides, and line length is capped at 68 characters (1.4.4, 1.4.10, 1.4.12, 1.4.8).
  • Diagrams are inline SVG with a title and long description, plus a caption that says the same thing in prose.
  • The tabs and the carousel in the Lab follow the WAI-ARIA Authoring Practices: one tab stop per tablist with arrow keys, focusable panels, and a carousel that never rotates by itself. Its slides are not interactive, so focus stays on the Previous and Next buttons and a polite live region announces only the slide's position and heading.
  • Posts are written in Markdown and rendered to static HTML at build time. The build refuses a post whose images lack alt text, whose headings skip a level, or whose body contains a second h1. Every post carries a dated byline, and the Atom feed carries the full text.
  • The résumé is a tagged PDF with a document title and language set, and every fact in it also appears as HTML in the Experience section, so the PDF is never the only route to the information.
  • No cookies, analytics, or third-party scripts. The theme choice is saved in your browser's local storage and never leaves it.

How it was tested

Every push to the repository runs the following before anything deploys:

  1. Token contrast build. 81 color pairs across three themes, checked with the WCAG 2.x relative-luminance formula. A failing pair stops the build.
  2. Unit and component tests with Vitest: keyboard behavior of the theme picker, the filter, and the contrast checker, plus the contrast math against the published WCAG example values.
  3. axe-core in a real browser with Playwright, using the WCAG 2.0, 2.1, and 2.2 A and AA rule sets and best-practice rules, on both pages and in all three themes. Zero violations is the pass condition.
  4. Keyboard walk with Playwright: the first Tab reaches the skip link, every interactive element is reachable in order, and the focused element is always inside the viewport.
  5. Reflow at 320 by 256 pixels: no horizontal scrollbar on either page.

Beyond the automated checks, I use the site the way I use everything else: with a screen reader and a braille display, keyboard only. Automated tools find roughly a third of accessibility problems; the rest is judgment, which is why the case studies describe behavior and not just markup.

Known limitations

  • The native color picker (<input type="color">) in the contrast checker is a browser control and its accessibility varies by browser. The adjacent hex text field does everything the picker does, and the two stay in sync.
  • The contrast checker's preview swatch shows sample text in exactly the two colors you enter. If you enter a failing pair, that sample fails by design; the verdict is in the table beside it, in words, and the swatch is hidden from assistive technology.
  • The architecture diagrams are simplified. The long description and caption are the reliable source; the picture is a summary.
  • Contrast is enforced for colors defined in the token file. If you override the theme with a browser extension or a user stylesheet, the site will respect it but can't vouch for the result.

Report a problem

If anything on this site is hard to use with your assistive technology, please tell me. Email meredith.laurel@gmail.com, open an issue on the GitHub repository, or message me on LinkedIn. Say which page, what you were trying to do, and what browser and assistive technology you use, and I'll fix it and tell you when I have.

Technical details

HTML, CSS, and TypeScript compiled with Vite. No framework runtime. Tested in Chromium via Playwright, and used daily by me with a screen reader (mostly JAWS) and a braille display on Windows. Source, tests, and this statement are in the public repository.
