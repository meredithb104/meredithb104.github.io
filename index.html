About

Most accessibility work happens after the fact: an audit, a spreadsheet of findings, a sprint of patches, and then the same findings a year later. I'd rather build so that the findings can't happen. That means using the platform before reaching for ARIA, treating a contrast failure as a build error, and testing the behavior a screen reader user notices first, not just the markup.

I work across the stack when a project needs it. The two bots in the case studies below are TypeScript on Node with Firestore, scheduled jobs, and language-model integrations, and they were built for real people with real deadlines: a household coordinating medical care, and a nonprofit running a social media pipeline with volunteers.

Outside of engineering, I'm the volunteer program and project coordinator for The NDProj, a community for neurodivergent and chronically ill students in higher education.

Case studies

Two production TypeScript applications I can't publish the source for. Here is how they're built and how they run.

Slack app · Node · Firestore · Gemini

MedConnect: appointments from screenshots to reminders

Coordinating care across many clinicians means appointments arrive as portal screenshots, confirmation emails, and half-remembered phone calls. MedConnect lives in the household's Slack and turns each of those into a structured record, a calendar event, and reminders for the patient and a support person.

How a screenshot becomes an appointment

  1. Someone @mentions the bot with an image. The handler checks the sender against an owner plus an allowlist of trusted uploaders from the environment; anyone else gets a polite refusal, and the image is never downloaded.
  2. One channel receives several kinds of screenshot (appointments, referrals, lab orders), so the image is classified before it is routed: a cheap Gemini vision call returns a type, and each type's handler either claims the mention or lets it fall through.
  3. The claiming handler asks Gemini for a typed JSON shape (title, date, times, category, doctor hint, address). Prompts live next to the type they produce; unparseable output is an error, not a guess.
  4. The doctor hint is matched against the directory with a fuzzy matcher: substring or Levenshtein distance for whole names, then per-token matching that ignores titles like "Dr." so they can't match every doctor at once. No match means the bot asks, with a one-click "add this doctor" flow, rather than booking with the wrong clinician.
  5. A single bookAppointment service creates the Google Calendar event, writes the Firestore record with the event ID, and formats the Slack card. The slash command and the mention path both call it, so there is one place where booking can be wrong.

Scheduled jobs

  • 40-minute reminders run every five minutes and pick appointments in a 35 to 45 minute window. Each record stores reminderSentAt, so the job is idempotent across restarts and never DMs twice.
  • Next-day follow-up at 11:00 America/New_York asks how yesterday's visit went and opens the record for visit notes and next steps.
  • Referral and lab-order reminders nudge until the referral is resolved, and support-person reminders go to the second person on an appointment.

Structure

Entry points
Slash commands /appointment, /doctor, /directory, /find; @mentions with text or an image; button and modal interactions.
Layout
commands/, interactions/, events/, jobs/, services/, db/, types/, utils/. Each feature exports a register(app) function; index.ts is only wiring.
Data
Typed Firestore documents: Appointment, DoctorCard, Referral, TestReferral. Optional fields are documented at the type, including which Slack ID is set by which UI control.
Integrations
Gemini over plain fetch (no SDK: one small function per prompt shape, typed return). Google Calendar through a service account. A hand-written RFC 5545 .ics generator with a VTIMEZONE block, so a support person without calendar access can still import the event.
Runtime
Node in a Docker image on Railway, restart-on-failure. Unhandled rejections and exceptions are logged with a prefix per module so production logs can be grepped by feature.

Decisions I'd defend

  • Classify before parse, because the channel is not a reliable signal of content.
  • Never invent a doctor. Ambiguity becomes a question with a button, not a best guess.
  • Idempotency lives on the record, not in process memory, so restarts are safe.
  • Slow work is visible work: the bot replies "Reading that referral…" immediately, then posts the result, so nobody wonders whether the mention landed.

Discord bot · Node · Firestore · Gemini · Google Calendar

PlannerBot: a project and social media pipeline for volunteers

The NDProj runs on volunteers with limited hours. PlannerBot lives in the team's Discord and gives them projects with tasks, to-dos with subtasks, events with conflict checks, and a social media pipeline where nothing is posted without a caption, a graphic, alt text, and an approval.

The post pipeline

One record per post through its whole life: Idea → Drafted → In review → Approved → Posted. Planned posts are the calendar; posted ones are the log; the same document is both.

  1. Capture. An @mention is routed by intent (post, to-do, or event) with explicit heuristics, then Gemini extracts topic, platform, owner, date, and content pillar. Attachments become files on the record.
  2. Private by default. Each post's card lives in its own private thread with the requester and owner; the channel gets a one-line pointer. Cards that predate this are migrated the next time they redraw.
  3. Readiness, not vibes. "Request review" runs a pre-flight checklist. A missing caption or a leftover [placeholder] blocks submission; missing hashtags, graphic, alt text, pillar, or date are warnings. The same rules drive the weekly cadence report, so the checklist and the report never disagree.
  4. Alt text is required to count. A post with a graphic and no alt text is not a finished post. The "copy caption" action sends caption, hashtags, and alt text as three separate messages so that a long-press on a phone copies exactly one.
  5. Drafting is assisted, not automatic. A "write draft" button asks what to steer toward, generates in the organization's documented voice with per-platform rules, and previews privately with shorter / warmer / more direct / try again. Nothing is saved until someone chooses it, and facts that weren't supplied come back as placeholders, never invented.

Cards that stay current

Every record renders to a "card" message. When anything changes, the card is edited in place if it is still the newest message in its channel, otherwise deleted and re-sent at the bottom so it stays next to where people type. Duplicates in one channel collapse to one. Nobody is ever asked to press Refresh.

Structure

Commands
One slash command per file (/project, /todo, /post, /event, /stats), listed once in commands/index.ts.
Interactions
Buttons, selects, and modals are keyed by customId prefix (prefix:arg1:arg2). A registry holds three handler maps; each feature module registers into them; one dispatcher splits the ID and calls the handler with its arguments.
Jobs
node-cron at 9:00: weekly digest, post reminders, content cadence, monthly social stats, metrics refresh from Instagram and LinkedIn providers, and release notes to a docs channel.
Documentation
A README for engineers and an HTML field guide for the team, served by the bot and pinned in Discord. Release notes are posted automatically on deploy.

Two production problems, solved

Overlapping deploys. Railway starts the new container before stopping the old one, and for those seconds Discord delivers every message and cron tick to both. A subtask once got two threads and a delete cascade ran halfway. Fix: on ready, each instance writes its ID to a settings document and subscribes to it; the moment a newer instance claims it, the older one ignores messages, interactions, and cron until it is stopped. The lock is per bot user, so a dev bot beside prod never silences prod.

Testing without touching prod. Feature branches run as a second Discord application in the same server with jobs disabled, no docs channel, and a separate lock. Component interactions always route to the app that owns the message, so prod cards and dev cards can't cross.

How I work

Five rules that show up in every project above, and in this page's source.

  1. Accessibility is a build error, not a review comment. The tokens on this site declare which colors sit on which backgrounds. The build computes every pair and refuses to emit CSS if one fails. While building this page, the check caught me asking a focus ring to contrast with both the page and a dark button; that isn't the ring's adjacent color, and the build said so before a reviewer had to.
  2. Use the platform before you use ARIA. Real buttons, real labels, native radio groups, native <dialog>. ARIA only where HTML has no answer: aria-pressed on a filter toggle, aria-current on the section you're reading.
  3. Focus goes where the user's attention should go. Skip links land on a focusable main. In-page links move focus to the section. Error summaries take focus. Nothing is disabled while it works, because disabled controls vanish from the tab order and go silent.
  4. Never color alone. Every state is also text: "Pass" and "Fail", a check mark on the pressed filter, an underline on the current section. Icons are hidden from assistive tech and sit next to a visible label.
  5. Test the behavior, not just the markup. axe-core catches missing names and bad roles; it cannot tell you focus went nowhere on submit. This site runs axe in a real browser on every push, and also tabs through the page, resizes it to 320 pixels, and checks that nothing scrolls sideways.

Tabs and a carousel

Two patterns that go wrong more often than they go right, built to the WAI-ARIA Authoring Practices. The tabs below are the demo: one holds the carousel, the others explain it and show the markup as authored. Without JavaScript they are a list of links and stacked sections; the carousel is twelve stacked cards. Nothing auto-rotates.

Demo

1. Disabled while loading

A submit button set to disabled while the request runs vanishes from the tab order and goes silent. The user presses Enter, nothing happens, and nobody tells them why.

Instead: aria-busy="true" and aria-disabled="true", keep it focusable, and announce the result when it comes back.

2. Icon buttons with no name

A magnifying glass is not a label. A screen reader announces "button" and nothing else, and a voice-control user has no word to say.

Instead: every icon-only control gets an accessible name, and the icon itself is aria-hidden.

3. Focus dropped on close

The dialog closes and focus lands on <body>. For a screen reader user that is a trip back to the top of the page.

Instead: return focus to the control that opened it. Native <dialog> does this for free.

4. Color as the only signal

Red border for error, green for success, and nothing else. That is invisible to a screen reader and to a lot of sighted people.

Instead: add text. Color can reinforce a state; it can never carry it alone.

5. Live regions mounted with content

A status region created at the moment it has something to say is usually silent, because the screen reader never saw it change.

Instead: mount it empty at startup, then write to it. Clear it first if you need to repeat the same message.

6. Placeholder as the label

Placeholders vanish on the first keystroke, most of them fail contrast, and a form full of typed values has no labels left at all.

Instead: a visible <label>, always. Hints go in aria-describedby.

7. A div that clicks

A <div onClick> is invisible to the keyboard, has no role, and no name. Adding tabindex gets you halfway to a worse button.

Instead: if it does something, it is a <button>. If it goes somewhere, it is an <a>.

8. The focus ring, removed

outline: none with nothing in its place means keyboard users cannot see where they are. It is usually done to hide the ring from mouse users.

Instead: style :focus-visible. Mouse users never see it; keyboard users always do.

9. Skipped heading levels

An h2 followed by an h4 because the h3 looked too big. Screen reader users navigate by heading level; the outline now has a hole in it.

Instead: heading levels are structure. Fix the size in CSS.

10. Errors nowhere near the field

A red list at the top of the form, no link to the field, and the field itself says nothing when you land on it.

Instead: aria-describedby the message, aria-invalid the field, and link each summary item to its input.

11. Hover-only tooltips

If it only appears on hover, keyboard and touch users never see it, and it disappears the moment a magnifier user moves toward it.

Instead: show it on focus too, let Escape dismiss it, and never put essential information there (WCAG 1.4.13).

12. Motion with no off switch

Auto-playing carousels, parallax, and animated counters with no pause control and no prefers-reduced-motion check.

Instead: nothing moves unless the user asks. This carousel does not auto-rotate, and its one fade is 0ms under reduced motion.

How it's built

Tabs follow the APG tabs pattern with automatic activation: one tab stop for the whole tablist, Left and Right arrows move and select, Home and End jump, and each panel is focusable so the next Tab press lands on the content rather than skipping past it. Selection is shown by weight and a thick underline, not color alone. The URL hash opens a panel on load. Without JavaScript the markup is a list of in-page links above stacked sections with headings; the script removes those headings because the tab now names the panel.

The carousel is the APG "tabbed carousel": the container is a group with aria-roledescription="carousel", the slide picker is a second tablist with one tab stop and arrow keys, and each slide is a tabpanel with aria-roledescription="slide" and an accessible name of "3 of 12". Non-current slides get the hidden attribute, so they leave the accessibility tree and the tab order together. Left and Right on the Previous or Next button also move slides, so it doesn't matter which one has focus.

Where focus goes after Next, and why. It stays on the button. The slide track is a polite live region, so a screen reader hears the slide that arrived without focus moving. Carousel guidance is genuinely contested on this point: one school says focus should move to the new slide so a screen reader user lands at the start of the new content; the other says that forcing focus onto a non-interactive slide puts a ring on something that does nothing and breaks a sighted keyboard user's flow through the controls. These slides are not interactive, so the second argument wins here, and the live region covers the first concern. A carousel whose slides hold headings, links, and menus is a different problem: those slides would need focus to move to their first element, and could not be driven as a "tab in, arrow within, tab out" widget at all. This component is scoped, on purpose, to slides you read.

Reading order is tab order. Controls sit above the track in the DOM and on screen; nothing is reordered with tabindex, so the page reads the same whether you arrow through it or tab through it.

What it refuses to do: auto-rotate. There is nothing to pause because nothing starts, and the live region can never interrupt someone reading elsewhere on the page. Dots are 24-pixel targets with a visible border. The selected dot is filled and larger, and under Windows High Contrast it uses the system highlight color.

Both elements share one small roving-tabindex helper, tested once. The Playwright suite tabs into each tablist, arrows through it, checks that hidden slides are not reachable, and confirms that Tab from the Next button leaves the carousel.
